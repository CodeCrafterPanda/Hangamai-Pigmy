# Seed Data Format

**The content in this folder is a sample dataset, not *the* dataset.** It exists so the app has
something to start with, and it is meant to be replaced by a real one. `types.ts` is the part
that is fixed: it is the contract every dataset must satisfy, derived from `types/entities.ts`.
Everything else here — `ids.ts`, `branch.ts`, `agents.ts`, `routes.ts`, `schemes.ts`,
`customers.ts`, `accounts.ts`, `delegations.ts`, `ledgerEntries.ts` — is data you may throw away
and rewrite.

Replacing it requires **no changes** under `utils/`, `slices/`, `scenes/` or `app/`. The loader
(`utils/seedData.ts`) reads whatever `index.ts` composes, resolves references and handles
idempotency; it never names a record, id or count from the sample. Validity is checked by the
compiler against `types.ts`, not by convention.

```
data/seed/
  types.ts          THE CONTRACT — the shape each entity file must satisfy
  ids.ts            sample: fixed ids + customer/account handles
  branch.ts         sample: 1 branch
  agents.ts         sample: agents
  routes.ts         sample: routes
  schemes.ts        sample: schemes
  customers.ts      sample: customers
  accounts.ts       sample: accounts (one per customer handle)
  delegations.ts    sample: delegations
  ledgerEntries.ts  sample: opening ledger entries (empty)
  index.ts          assembles the above into `seedDataset`
```

## Two kinds of identity

| Entity                                    | Id source                             | How the dataset references it   |
| ----------------------------------------- | ------------------------------------- | ------------------------------- |
| branch, agent, route, scheme, ledger entry | fixed id declared by the dataset      | by the id constant              |
| customer, account, delegation             | generated by the reducer at seed time | by a `ref` handle               |

The reducers `addBranch` / `addAgent` / `addRoute` / `addScheme` / `addLedgerEntry` upsert on the
id they are given, so re-running the seed re-applies those records in place. `addCustomer` /
`addAccount` / `createDelegation` mint their own ids, which is why the dataset cannot name them
directly. Instead each customer carries a `ref` handle and each account carries its own `ref`;
accounts and delegations point at a customer via `customerRef`, and opening ledger entries point
at an account via `accountRef`. The loader resolves every handle to the id the reducer actually
assigned.

Handle *values* never reach the store — they are internal to the dataset, so a replacement is
free to name them however it likes, as long as `types.ts` still derives the handle types from the
maps in `ids.ts`.

**Ids and handles must stay stable within a dataset.** Changing a value in `ids.ts` orphans every
reference to it; renaming a handle breaks the wiring that depends on it.

## Required fields per entity

`types.ts` is authoritative — it derives each seed shape from the corresponding entity type in
`types/entities.ts`, minus the fields the loader supplies. In particular:

- **`createdAt` is never written in the dataset.** The loader stamps the seed-run timestamp on
  branch, agents, routes, schemes and opening ledger entries; customers, accounts and delegations
  get theirs from their reducers.
- **`SeedBranch`** — `id`, `coopId`, `code`, `name`, `address`, `timezone`. `timezone` is the
  branch business-date source; every collection is booked against a date derived from it.
- **`SeedAgent`** — `id`, `branchId` → branch id, `name`, `agentCode`, `phone`, `status`.
- **`SeedRoute`** — `id`, `branchId` → branch id, `routeCode`, `name`.
- **`SeedScheme`** — `id`, `branchId` → branch id, `name`, `frequency`, `minAmount`,
  `penaltyPerDay`, `penaltyType` (MVP uses `NONE`, which keeps the effective penalty ₹0).
- **`SeedCustomer`** — `ref` handle, `branchId` → branch id, `routeId` → route id,
  `primaryAgentId` → agent id, plus name/phone/address fields and `status`. The pair
  `fullName` + `phone` must be unique across the list (see idempotency below).
- **`SeedAccount`** — `ref` handle, `customerRef` → customer handle, `schemeId` → scheme id,
  `installmentAmount`, `status`. `accountNumber` is optional; omit it to take the generated
  `ACCT-YYYY-NNNN` series. Give each customer **at most one** account: the idempotency guard
  below creates an account only for a resolved customer who has none yet, so a second account for
  the same customer is silently skipped.
- **`SeedDelegation`** — `customerRef` → customer handle, `primaryAgentId` (must match that
  customer's own `primaryAgentId`), `secondaryAgentId` (the agent receiving the work),
  `durationDays` (window length from the seed run), `createdBy`. Leave `accountId` out to cover
  all of the customer's accounts.
- **`SeedLedgerEntry`** (optional, `ledgerEntries` may be omitted or empty) — dataset-supplied
  `id`, `accountRef` → account handle, `entryType`, `amount`, `narration`, `postedAt`, optional
  `collectionId`. Use this only for **opening balances** carried over from another system, posted
  as `ADJUSTMENT`. The balance shown in the app is derived from the ledger
  (`selectAccountBalance`), so an opening entry is picked up without touching the
  `Account.currentBalance` cache, which the collection flow maintains on its own.

Collections and settlements are **not** seedable, by design: `commitCollection` is the live
business flow (idempotency keys, receipt numbering, ledger side effects), and fabricating a
`Collection` record would claim an agent collected money that nobody collected. An opening
balance is a ledger fact, so it is expressed as a ledger entry instead — the ledger stays a
truthful record of what the app actually did.

## Idempotency and protection of agent-created data

Seed-once is decided outside this folder, in `app/_layout.tsx`, via `hasCompletedSeed()` /
`markSeedCompleted()` against `StorageMetadata.seedVersion`. The loader is written so that
running it a second time (the recovery path, when the seed marker survived but the persisted
baseline did not hydrate) adds nothing new:

- fixed-id entities are re-applied in place, not duplicated;
- a dataset customer is skipped when a customer with the same `fullName` + `phone` already
  exists;
- an account is created only for a resolved dataset customer who has no account yet;
- a delegation is created only when no live delegation with the same
  customer/primary/secondary trio exists;
- an opening ledger entry is written under the id the dataset gave it, so it overwrites itself
  rather than posting twice.

A customer an agent entered in the field never matches a dataset `fullName` + `phone`, so neither
they nor their accounts are ever touched by a re-seed. This holds for any dataset content, not
just the sample.

## Replacing the dataset

1. Rewrite the content files (or delete them and add your own). `index.ts` composes the dataset
   from named exports — `seedBranch`, `seedAgents`, `seedRoutes`, `seedSchemes`, `seedCustomers`,
   `seedAccounts`, `seedDelegations`, `seedLedgerEntries` — so either keep those export names or
   adjust `index.ts` to match. Counts are free: any number of agents, routes, schemes, customers
   or accounts works.
2. Declare your own fixed ids and handle maps in `ids.ts`. `SEED_CUSTOMER_REF` and
   `SEED_ACCOUNT_REF` are the only two the types read; their keys and values are yours to choose.
3. Point `session` at an agent id and branch id that exist in your dataset.
4. Keep every foreign key pointing at something that exists in the dataset — a customer with an
   unknown `routeId`, or an account with an unknown `customerRef`, will simply not be wired up.
5. Let the compiler check it: if `seedDataset` still satisfies `SeedDataset`, the loader will
   take it as-is. Nothing under `utils/`, `slices/`, `scenes/` or `app/` needs to be edited.
6. If the change alters the **identity** of records already on installed devices — a different
   fixed id, or a changed `fullName`/`phone` on a customer — bump `CURRENT_SEED_VERSION` in
   `utils/storage.ts`. Those devices then re-seed once instead of ending up with a mix of old and
   new records. Purely additive changes to fields nothing reads do not need a version bump.
